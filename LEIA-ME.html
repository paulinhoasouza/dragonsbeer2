DRAGONS BEER · SUPABASE + CLOUDFLARE

Da instalação ao primeiro pedido.

O pacote contém a aplicação, o banco, o cardápio do HTML original e os testes. Siga a ordem abaixo. Não é necessário criar tabelas manualmente.

Situação da entrega: código implementado e testes locais realizados. O app ainda precisa ser instalado no seu Supabase e publicado no seu Cloudflare. O pacote não contém suas credenciais.

1. Criar o banco no Supabase

  1. Crie um projeto novo, exclusivo para este bar. Não execute os scripts no banco de propostas ou em outro sistema.
  2. Abra SQL Editor → New query. No pacote, abra supabase/01-schema.sql em um editor de texto, copie todo o conteúdo e execute no SQL Editor. Execute este arquivo apenas uma vez.
  3. Crie outra consulta e execute todo o arquivo supabase/02-cardapio.sql. Ele importa os 41 produtos do HTML que você enviou. Confira preços e disponibilidade depois.
  4. Em Authentication, localize a configuração de provedores/sign-in e ative Anonymous sign-ins. Os clientes usam uma sessão anônima vinculada ao navegador.
  5. Mantenha o provedor Email ativo para a equipe. Não é necessário permitir cadastro público de funcionários.

Os dados ficam no schema dragons. No Table Editor, selecione esse schema para inspecionar tabelas. Não adicione dragons aos schemas expostos da API. O frontend usa somente a função pública db_action, que verifica as permissões.

2. Criar seu primeiro administrador

  1. Vá a Authentication → Users → Add user → Create new user.
  2. Informe seu e-mail e uma senha forte. Marque Auto Confirm User, se essa opção aparecer. Guarde essa senha; não precisa enviá-la no chat.
  3. Abra supabase/03-primeiro-admin.sql. Substitua SEU_EMAIL_AQUI pelo mesmo e-mail criado e SEU_NOME_AQUI pelo seu nome.
  4. Execute o arquivo editado no SQL Editor. Se o e-mail não existir em Authentication, o script mostrará erro explicando o que corrigir.
Criar usuário em Authentication e atribuir permissão em dragons.staff são duas etapas diferentes. O terceiro script faz a vinculação. Sem ele, o login pode existir, mas o app negará acesso.

3. Publicar o código no Cloudflare

  1. Extraia o ZIP. Crie um repositório GitHub e envie o conteúdo da pasta dragons-beer.
  2. A raiz do repositório deve ter package.json, package-lock.json, worker.js, wrangler.jsonc e as pastas src e public. Não envie node_modules.
  3. No Cloudflare, abra Workers & Pages → Create → Import repository e selecione o repositório.
  4. Escolha a opção de Worker e use as configurações abaixo. Os nomes dos menus podem variar conforme a interface da plataforma.
CampoValor

Use Node.js 22 ou superior. Se escolher outro nome de Worker, altere também name no arquivo wrangler.jsonc para o mesmo nome.

Não é necessário informar “dist”: este Worker já declara public como pasta de arquivos e usa um endpoint próprio para a configuração.

4. Conectar o Supabase ao Worker

No Supabase, copie a Project URL e a Publishable key nas configurações de API / janela Connect. No Cloudflare, abra o Worker → Settings → Variables and Secrets.

Nome exatoValor
SUPABASE_URLURL do seu projeto, no formato https://SEU-PROJETO.supabase.co
SUPABASE_PUBLISHABLE_KEYChave pública sb_publishable_... ou chave legacy anon
TURNSTILE_SITE_KEYOpcional: chave pública do widget, se ativar CAPTCHA no passo abaixo

Não use service_role, sb_secret, senha do banco nem senha de usuário. As duas primeiras variáveis são públicas e serão enviadas ao navegador. As permissões estão protegidas no banco.

Salve as variáveis e faça uma nova publicação/deploy. Não é preciso editar o HTML com essas informações.

Proteção da entrada de clientes

Antes de abrir o acesso ao público, configure Cloudflare Turnstile e ative a proteção CAPTCHA no Supabase Auth. Cadastre o domínio final do app no widget. A chave secreta correspondente fica somente no Supabase Auth; a chave pública do widget vai em TURNSTILE_SITE_KEY no Worker. Reveja também o limite de logins anônimos por IP para o número de clientes que usarão o mesmo Wi-Fi.

5. Preparar a operação

Depois de publicar, use a URL devolvida pelo Cloudflare com os caminhos:

TelaCaminhoAcesso
Administração/adminAdministrador
Caixa/caixaCaixa ou administrador
Cozinha/cozinhaCozinha, caixa ou administrador
Bar/barBar, caixa ou administrador
Cliente/cliente?acesso=…QR Code/link gerado pelo caixa
  1. Entre em /admin com seu e-mail e senha do passo 2.
  2. Cadastre as mesas reais na aba Mesas. Não foram inventados números de mesa.
  3. Confira o cardápio. É possível cadastrar, editar preço, alterar setor e desativar produtos.
  4. Para cada funcionário, crie o usuário em Supabase Authentication e depois use Equipe → Vincular usuário no app para escolher o perfil.
  5. Abra cada setor em seu próprio dispositivo ou aba. Clique em Ativar som nos terminais do caixa, bar e cozinha. Mantenha-os abertos e ativos.

Funcionários compartilham a sessão da equipe nas abas do mesmo navegador. Use perfis de navegador separados se quiser testar usuários diferentes no mesmo computador. A sessão do cliente é separada da sessão da equipe.

6. Testar um atendimento completo

  1. No caixa, abra uma mesa e escolha compartilhada. Abra QR Code / acesso.
  2. Entre pelo QR em dois celulares. Cada cliente informa o nome. Ambos devem ver a mesma comanda.
  3. Envie um pedido com um alimento e uma bebida. Confirme que aparecem nos setores corretos.
  4. Avance os itens por Iniciar preparo → Marcar como pronto → Confirmar entrega.
  5. No cliente, peça a conta e escolha a forma de pagamento. O caixa deve mostrar o aviso, sem fechar a comanda automaticamente.
  6. No caixa, clique em Assumir atendimento. Confira a confirmação exibida ao cliente.
  7. Abra a comanda e registre o recebimento somente depois de conferir o valor. Itens ainda não entregues bloqueiam o pagamento; é preciso entregar ou cancelar com motivo.
  8. Libere a mesa e confira o relatório de vendas. O QR antigo não deve aceitar novos clientes.
  9. Abra novamente, agora com comandas individuais. Entre pelos dois celulares e confirme que cada um vê apenas sua comanda. O caixa deve ver as duas na mesma mesa.
  10. Desconecte e reconecte um terminal. A interface deve indicar falha e recuperar os dados. Um pedido com envio incerto deve ser reenviado pelo botão de confirmação pendente, preservando o mesmo identificador.

Os testes no banco real produzem registros reais. Faça a validação em um projeto de homologação antes de abrir a operação, ou identifique claramente os atendimentos de teste. O app preserva os registros; não há botão de apagar todo o histórico.

Como os avisos funcionam

Com a tela aberta, as informações são buscadas automaticamente a cada 4 segundos. Pedido de conta gera cartão persistente no caixa, contador no título da aba, aviso na tela e som após ativação. O alerta deixa a fila pendente quando alguém assume o atendimento.

Notificações do sistema são opcionais e dependem da permissão e do suporte do navegador. Não há push com o app fechado. Navegadores podem suspender abas e atrasar atualizações quando o aparelho está bloqueado. Use os terminais ativos durante a operação.

Regras que vale conhecer

  • QR por atendimento: é renovado a cada abertura da mesa. Exiba ou imprima o QR atual; esta versão não usa QR fixo.
  • Conta compartilhada: qualquer membro admitido vê a conta inteira e pode solicitar seu fechamento.
  • Conta individual: um navegador/celular por comanda. Apagar dados ou trocar de aparelho não recupera automaticamente o acesso; o caixa mantém o registro.
  • Pagamento presencial: o app registra o que o caixa confirmou. Não processa Pix/cartão, não emite nota fiscal e não adiciona taxa de serviço.
  • Sem divisão parcial: para cobrança individual, escolha esse modo ao abrir a mesa. Transferência de consumo e estorno de pagamento não fazem parte desta versão.
  • Relatório: considera o horário do recebimento, no fuso de Cuiabá, e exclui itens cancelados.

Arquivos e validação

src/app.js contém a interface; worker.js serve os arquivos/configuração; supabase contém o banco; tests contém os testes automatizados. O README.md detalha arquitetura e limites.

Validação local: 26 cenários de banco em PostgreSQL embarcado e 6 cenários de interface em DOM simulado. Não houve teste visual em navegador nem integração com seu Supabase/Cloudflare reais.
